# ArtQuest 上线操作指南

**场景**：一台别人账号买的、已经在跑别的服务的阿里云 ECS。
**目标**：把 ArtQuest 跑在上面，**让别人（孩子、家长、老师）都能打开用**。

> 上一版指南是"自己远程访问"，走 SSH 隧道。目标改成公开访问之后那条路作废了——
> 隧道只有你一个人能用。这一版换成 **Caddy 反代 + 域名 + 自动 HTTPS**。

---

# 第零部分 · 现在的实际情况

**域名：`art.ddhulu.cn`｜服务器：`124.220.179.33`（腾讯云，上海）**

探测下来，原先三个卡点里**两个已经不存在了**：

### ✅ 备案：过了

`http://ddhulu.cn` 返回 200。大陆 IP 的 80 端口能正常对外服务，这就是 ICP 备案
完成的硬证据——没备案的话阿里云/腾讯云会在入口直接拦掉。

**原先估的 1–3 周最大风险，消失了。**

### ✅ 80/443：Caddy 在跑，443 已开

`Server: Caddy`——不是 nginx。这是好消息，Caddy **自己申请和续期 Let's Encrypt
证书**，不需要 certbot，配置也短得多（见 `Caddyfile.artquest`，总共十几行）。
443 端口实测是通的，安全组不用再动。

### ⚠️ 还没做：DNS

`art.ddhulu.cn` **目前没有 A 记录**。这是现在第一件要做的事，而且**必须排在改
Caddyfile 之前**——Caddy 要先能解析到这个域名才签得到证书，顺序反了它会反复
重试、一直拿不到 HTTPS。

```
类型  A
主机记录  art
记录值  124.220.179.33
```

### ⚠️ SSH 不在 22 端口

22 端口是「**拒绝连接**」而不是超时——安全组通了，但那个端口上没有服务，
说明 SSH 被改到别的端口了。这个只能问对方。

### ✅ 已根治（2026-09-26）：应用层有鉴权了

下面这一段记录的是**改之前**的口子，留着当理由。现在 `main.py` 里「谁在说话」那一节：
研究员接口要 `Authorization: Bearer $ARTQUEST_ADMIN_TOKEN`（不设就全关）；`account_id`
必须配那个账号的登录令牌；`/api/v1` 版本化；CORS 放行 iOS 壳。服务器 `.env` 里**必须**加
`ARTQUEST_ADMIN_TOKEN`，重启服务。Caddyfile 里的 basic_auth 那段已经删掉——两层各要一套口令
只会让研究员的 curl 更难写，而且 matcher 漏一条就漏一个接口的问题在应用层不存在。

原来的问题：`artquest/main.py` 里没有一个 `Depends`、没有任何 `Authorization` 校验。
账号系统发了 token，但没有端点验证它——`account_id` 只是个筛选参数，谁传谁生效。

| 接口 | 公网上的后果 |
|---|---|
| `GET /api/sessions`（不带参数） | 返回**全部**孩子的 session 列表 |
| `GET /api/sessions/{sid}` | 拿到上面的 id 就能读任何完整记录 |
| `/files/{sid}/*.png` | 同上，直接看到画 |
| `POST /api/gallery/curate` | 任何人可触发策展，无鉴权写入 |
| `/api/participants/{pid}/*` | 别人的成长数据、实验协议 |

`session_id` 是 `uuid4().hex[:12]`（48 位随机，不可枚举），单看 `/files/` 算
「不可猜的分享链接」，尺度可接受。**问题是 `GET /api/sessions` 把这些 id
一次性全发出去了。**

`Caddyfile.artquest` 已经把这三处挡在口令后面，但那是止血——漏一条 matcher
就漏一个接口。根治要在应用层加 token 校验，见第三部分。

## 📧 第一封 · 现在就发

> 想在服务器上跑一个小的 Python 后端（FastAPI，几十 MB，无数据库，纯文件存储，
> 常驻内存约 150MB），域名用 `art.ddhulu.cn`。
> 它**只监听 `127.0.0.1:8010`，不自己对公网开端口**，对外走你现有的 Caddy 反代，
> 不抢你任何端口。
>
> ### 1）加一条 DNS（这条最好先做，Caddy 要靠它签证书）
>
> ```
> 类型 A ｜ 主机记录 art ｜ 记录值 124.220.179.33
> ```
>
> ### 2）建个账号给我，以 root 执行
>
> ```bash
> useradd -m -s /bin/bash ray
> install -d -m 700 -o ray -g ray /home/ray/.ssh
> echo 'ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIHJJX/RPb1+IS8KY/01TWaFY17HBnPn+0WvWA5omSG9s ray@artquest' >> /home/ray/.ssh/authorized_keys
> chown ray:ray /home/ray/.ssh/authorized_keys
> chmod 600 /home/ray/.ssh/authorized_keys
> ```
>
> **验证，三行都要对：**
>
> ```bash
> ls -ld /home/ray/.ssh                              # drwx------ ray ray
> ls -l  /home/ray/.ssh/authorized_keys              # -rw------- ray ray
> grep -c artquest /home/ray/.ssh/authorized_keys    # 1
> ```
>
> ### 3）告诉我四件事
>
> 1. **SSH 是哪个端口？**（我试了 22，是拒绝连接）
> 2. 给没给我 sudo？（不给也行，我装自己家目录）
> 3. **8010 端口空着吗？**被占了帮我换一个
> 4. Caddyfile 在哪、由谁改？
>
> ### 说明
>
> **①** 不需要给我私钥，公钥装上就行，你那边不用保管任何东西。
> **②** 不用给账号设密码。不设密码时密码登录是锁着的，公钥登录照常，更安全。
> **③** 权限必须严格：`.ssh` 700、`authorized_keys` 600、属主都是 ray。
>   这三样错任何一样 sshd 都会拒绝登录、且日志里不明说原因——这是公钥登录
>   失败最常见的原因，第 2 步的验证就是查这个。
> **④** 愿意给 sudo 的话：`usermod -aG sudo ray`，因为账号没密码得同时配免密：
>   `echo 'ray ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/ray && chmod 440 /etc/sudoers.d/ray`

## 📧 第二封 · 部署完成后再发

> 服务跑起来了，在 `127.0.0.1:8010`。现在接一下 Caddy 就能对外访问了。
>
> 配置我写好了，在 `/home/ray/artquest/deploy/Caddyfile.artquest`，你可以先看一遍。
> 它做两件事：把 `art.ddhulu.cn` 转给 `127.0.0.1:8010`，以及把三个研究员接口
> 挡在口令后面。
>
> ### 1）生成口令的哈希
>
> ```bash
> caddy hash-password          # 交互式输入，把输出那串 $2a$... 贴进配置里
> ```
>
> 配置里两处 `REPLACE_WITH_BCRYPT_HASH` 都换成它。设的口令告诉我一下。
>
> ### 2）追加到 Caddyfile
>
> ```bash
> cat /home/ray/artquest/deploy/Caddyfile.artquest >> /etc/caddy/Caddyfile
> caddy validate --config /etc/caddy/Caddyfile     # 先验语法，报错就别往下走
> caddy reload  --config /etc/caddy/Caddyfile      # reload 不中断现有站点
> ```

> 前提是那条 A 记录已经生效（`dig art.ddhulu.cn` 能解析出来）。

>
> 删掉 Caddyfile 里那一段再 `caddy reload` 就行，你其余站点不受影响。
> 我的服务也可以随时 `systemctl stop artquest` 停掉。

# 第四部分 · 部署

## 1. 试连

```bash
ssh -i ~/.ssh/aliyun_ed25519 ray@<IP>        # 端口非 22 加 -p <端口>
```

## 2. 写进 ~/.ssh/config

```
Host aliyun
  HostName <IP>
  Port <端口>
  User ray
  IdentityFile ~/.ssh/aliyun_ed25519
  ServerAliveInterval 30
```

`ServerAliveInterval` 是给 VSCode Remote-SSH 用的，不加的话远程窗口挂几分钟会断线。

## 3. 摸清这台机器（只看，不改）

```bash
ssh aliyun 'free -h; df -h /; nproc; ss -tlnp 2>/dev/null | head -20'
```

重点看**已占用的端口**，确认 8010 空着。顺便看内存——
如果机器很小，别用 VSCode Remote（vscode-server 常驻 300–500MB），
改用本地编辑 + `push.sh` 推送。

## 4. 部署

```bash
cd ~/桌面/ArtQuest && ./deploy/push.sh
```

有 sudo 走这个（装 `/opt/artquest` + systemd）；没 sudo 我会给你改成家目录版本。

## 5. 请对方接上 Caddy（见第二封信）

见第二部分步骤 5。

## 6. 验收

```bash
curl -I https://art.ddhulu.cn/                 # 200，证书有效（Caddy 自动签的）
curl -I https://art.ddhulu.cn/api/sessions     # 必须 401，被口令挡住
```

第二条返回 200 就说明第三部分没生效，**立刻停下**。

# 第五部分 · 出错怎么查

## 1. 连不上：三种表现三种病

| 报错 | 病因 |
|---|---|
| `Connection timed out` | 安全组没放行，或 IP/端口写错 |
| `Connection refused` | 地址通了但那个端口没有 sshd |
| `Permission denied (publickey)` | 端口通了，纯粹是密钥或权限问题 |

## 2. publickey 被拒，按顺序查

1. 本机 `ssh -v -i ~/.ssh/aliyun_ed25519 ray@<IP>` 看送了哪把钥匙
2. 请对方看服务器日志（客户端报错是故意模糊的）：
   `tail -30 /var/log/auth.log`（CentOS 系是 `/var/log/secure`）
3. 九成是步骤 3 那三个权限之一不对

## 3. 域名打不开

1. `dig art.ddhulu.cn` —— A 记录加了吗、生效了吗（Caddy 签证书全靠它）
2. `curl -I http://<IP>:8010/` 在服务器上跑 —— 应用自己活着吗
3. `caddy validate --config /etc/caddy/Caddyfile` —— 配置语法
4. `journalctl -u artquest -n 50` —— 应用日志
5. ~~没备案~~ —— 这条已经排除了：`http://ddhulu.cn` 返回 200，备案是过的

# 第六部分 · 这台机器上不要做的事

它是别人的，正跑着别人的服务。

1. 不要 `apt upgrade`、不要改 `sshd_config`、不要动防火墙
2. 不要 `systemctl restart caddy`——要动只能 `caddy reload`，而且先 `caddy validate`
3. 不要重启机器
4. 不要用 `0.0.0.0` 监听——只绑 127.0.0.1，对外交给 Caddy
5. 不要把私钥发给任何人，也不要接受别人发来的私钥

# 第七部分 · 两件需要你自己决定的事

## 1. 孩子的画放在别人的机器上

对方是 root，技术上能看到 `data/` 里全部作品和账号数据。
这不是信任问题，是事实——**root 就是能看**。

先用 `data/_trial` 跑通全流程没问题。真实作品上线前，
这件事该在 `docs/ETHICS.md` 里有个明确说法。

## 2. 四位暗号在公网上的强度

一万种组合，`accounts.py` 里有"连错 5 次冷却一分钟"挡着——
这个设计对**单个账号**是够的。但公网上多了一种局域网里没有的攻击：
拿常见名字 + 固定暗号去横着撞一大批账号，每个账号都只错一两次，冷却永远触发不了。

真要公开，值得加一条按 IP 的全局限速（Caddy 的 `rate_limit` 或应用层都行）。
这个决定取决于你打算让多少人用、是不是开放注册。
